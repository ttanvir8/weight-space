§1What the repository is

This repository holds the complete logs of the eight experiments in the blog post "Sparks of Weight Space Programming: LLMs can understand and write neural network weights". The first guide explained the theory of the post. This guide explains the evidence behind it.

For each experiment, the repository gives five kinds of evidence:

  • everything the authors sent to the model;
  • everything the model sent back, with its reasoning summaries where they exist;
  • every piece of code the model ran, with the output that it saw;
  • the evaluation behind each number in the post;
  • the networks that the model read or wrote.

The repository does not hold a program to run the whole study. It holds records. It also holds the scripts that build, train, apply, and score the networks.

Key facts from the repository

  • "Astra" is a real model name. The root README says that Astra is OpenAI's gpt-6-astra.
  • One turn is one Codex call. The authors call the Codex CLI with codex exec. They continue a conversation with codex exec resume <thread>.
  • No built-in tools. The authors switched off every Codex tool. They audited every turn. All 1,125 turns are tool-free.
  • Code goes through the authors' sandbox. In Experiments 3, 6, 7, and 8, the model writes a Python block. The harness runs it and sends the output back.
  • Only the reported runs are here. Trial runs of earlier prompt versions are not in the repository.

§2Terms

Each term has one meaning in this guide.

Codex CLI
A command-line program. The authors use it as the way to call the model.
turn
One call of codex exec. One message goes in. One reply comes out.
conversation
A series of turns that share one thread. Each thread has an id such as id-d085bb68.
reasoning effort
A setting per call: high, xhigh, or max. A higher setting lets the model think longer.
reasoning summary
A short text that the model gives about its thinking. Some runs have it. Some runs do not.
event stream
The raw record of one turn, in events.jsonl.
audit
A check of the event stream. A turn is tool-free when the stream holds only messages, reasoning summaries, and one Codex notice.
sandbox
A closed Python area. It has no network. The authors use bubblewrap (bwrap) to make it.
pass
One use of a probe that runs the network: a game pass, a position pass, or a forward-pass call.
nudge
A message from the harness that asks the model to test one more idea before it finishes.
handoff
A new conversation that continues old work. The harness gives it the task, the notes, and the current edit.
edits block
A code block that sets weights, one statement per line. Example: actor0.W[6, 122] = 80.
head-to-head
Games where two networks play each other.
placeholder
A short tag such as <data> that replaces a private path.
.npz / .npy
NumPy files. They hold arrays of numbers.
manifest
A list. It names the files or tensors in a set, with sizes and hashes.
diff
The difference between two models. The repository stores edits as a diff from the public base model.
SHA-256
A hash. It proves that a file has not changed.
truth / answer key
The correct answer. The model never saw it. Only the scorer reads it.

§4The harness folder

The harness/ folder holds the three files that set the rules for every call.

4.1 codex_config.toml

The file gives the default "no tools" setup. The comment in the file says: "every built-in capability that gives the model a tool is switched off; experiments that need tools add their own MCP server explicitly."

  • Model and effort. The file sets gpt-6-luna and medium as defaults. Each call overrides both. The experiments use gpt-6-astra and the efforts in the table below.
  • Safe mode. approval_policy = "never", sandbox_mode = "read-only", and web_search = "disabled".
  • Agents off. [agents] enabled = false.
  • Features off. The [features] list sets 22 flags to false. They include shell_tool, unified_exec, view_image, image_generation, multi_agent, plugins, browser_use, computer_use, and code_mode.
  • Instructions. The file points to instructions_neutral.md in the Codex home folder.

4.2 instructions.md

The file has one line: "Answer the user's request." Every run folder keeps a copy named instructions.md.

4.3 sandbox.py

The file is the Python sandbox for the Go experiment. The file docstring says that it works like the sandbox of the math experiment.

  • Isolation. The command uses bwrap --unshare-all --die-with-parent --new-session --clearenv. The system folders are read-only. /tmp is a fresh memory folder.
  • Work folder. /work is read-write. It stays between runs. It holds the network (net/<name>.npy), the pass results, and the model's files.
  • Libraries. numpy, scipy, scikit-learn, PyTorch (CPU), pandas, sympy, networkx. No Go library. No network. No GPU.
  • Limits. 900 seconds and 96 GB of memory for each run. The output stops at 20,000 characters.
  • Prelude. The harness adds helper code before the model's code. It defines SHAPES, NAMES, load(name), save(name, array), saved(), inp(row, col, plane), mv(row, col), and PASS = 81.
  • Safety checks in save(). The name must be known. The shape must match. All numbers must be finite.
  • Log. Each run appends one JSON line with the time, the code, and the first 6,000 characters of the output.
  • Input index. inp(row, col, plane) = (row × 9 + col) × 3 + plane. The output index mv(row, col) = row × 9 + col. Index 81 is the pass move.

§5The run loop (Experiments 3, 6, 7, 8)

When the model may use code, the harness runs a loop. The model has no tool of its own. It must write a code block in its reply. The harness reads the reply and acts.

  1. The harness sends the first message (turns/t001/prompt.txt). It holds the task, the rules, and the question.
  2. The harness calls codex exec. It audits the event stream. It writes run.json, events.jsonl, and answer.md.
  3. The harness looks at the reply.
    • If the reply has a python block, the harness runs it in the sandbox. It logs the code and the output in tool_calls.jsonl.
    • In Experiment 6, a games block or a positions block is one pass. In Experiment 7, an attention block calls the attention tool. In Experiment 8, a forward block is one pass.
    • If the reply has no code block, the harness takes it as the final answer.
  4. The harness sends the printed output as the next message (turns/tNNN/prompt.txt) in the same conversation.
  5. The loop ends when the model gives a final answer. Some experiments force the loop to go on: Experiment 6 reminds the model while passes are left. Experiment 7 sends nudges. Experiment 8 runs until every pass is used.

Special rules by experiment

  • E3. A turn with an empty final message is discarded. The harness waits 60 seconds and asks again in a new conversation (english_r0/turns/t001/fail1_*).
  • E6. The harness stopped for about 2 h 15 min at turn 63 of the 50-pass run. The failed calls are in turns/t063/fail*. The conversation then went on with its context intact.
  • E7. The attention tool crashed on the authors' side for 40 minutes. The harness retried with the model's recorded reply. The model never saw the failure. For this reason the tool calls start at number 5.
  • E8. After every 40 turns, or after a restart, the harness starts a new conversation (a handoff) with the task, the notebook, and the current edit. From an early turn on, a block that has no plain-English explanation is sent back unrun (at most twice in a row). The harness also sends notices (notices/001–004).

§7How to trace a number from the post

Each experiment README has a table "The post's numbers and where they come from". Use it as the map.

  1. Find the number in the post.
  2. Open the root README. Find the folder in the first table.
  3. Open the README of that folder. Find the row for the number.
  4. Open the named file. It is nearly always in eval/.
  5. If you want to see how the model got there, open the run folder: prompt.txt, then answer.md or turns/, then tool_calls.jsonl.
  6. If you want the network itself, open networks/.

What the folder shows

  • Networks. Three character-level transformers: 4 layers, 6 heads, width 384, MLP width 1,536, context 128, 28 characters, 7.16 million weights, trained on 1 billion characters with AdamW. All texts are lowercase, indentation kept, every other non-letter becomes a space.
  • Message. It holds the exact forward code of the network, the training method, the three candidate texts, the rules, and the question. The weights are not in the message. The model reads them in Python, as dict W.
  • Block keys. ln1_w, ln1_b, W_q, W_k, W_v, W_o, ln2_w, ln2_b, W_fc, W_proj for each layer 0 to 3. Matrices are (out, in).

The Python training text

The text is other projects' code, so the authors do not release it. They release a manifest and a rebuild script. The text came from 36,651 distinct .py files in the site-packages of their environments. They removed docstrings and comments (ast.unparse), normalized the code, and joined the files. The result is 324,932,625 characters. The last 5,000,000 are held out.

  • Identified: 31,857 file entries (264.8 M characters, 81.5%).
  • Not identified: 4,096 stretches (60.1 M characters, 18.5%). They come from package versions that are no longer installed. files.tsv gives each stretch a position, a length, and a SHA-256, so a reader can test a candidate file.
  • The text was built with CPython 3.10.12. The rebuild script matches the start of the original text (first 33 files, 313,661 characters).

What the folder shows

  • Network. 243 → 512 × 6 → 82, ReLU, 1,480,274 numbers, all zero at the start. Input: 3 planes over 81 points (mover's stones, opponent's stones, White to move). Output: one logit per point and one for pass. Illegal moves are masked. Moves are sampled at temperature 1. There is no search.
  • Three block types. The model replies with a python block (one sandbox run), a games block (one pass), or a positions block (one pass).
  • Games pass. It plays up to 128 games of the current network against practice opponents: "random", "weak" (a REINFORCE network), and "strong" (a PPO network, seed 1). The model gets a summary and every game's moves in /work/pass_<k>/.
  • Positions pass. It runs the network on up to 256 positions. It returns top moves, logits, probabilities, and (on request) hidden activations.
  • Forbidden. Training or fitting weights to data. Search of any kind. Running the network outside the passes. Allowed: weights from its own design, Go-rule code that does not run the network, and analysis of pass results.
  • Scoring (hidden). 2,000 games against each of two small PPO networks (243 → 32 → 32 → 82, seeds 0 and 2). The written network plays Black in half the games. Komi is 7.5, so there are no draws.
  • Same-size PPO baseline. A 512 × 6 ReLU network trained by PPO for 20,000 iterations of 1,024 games (20.5 M games). The learning rate 3e-5 was chosen from 1e-4, 3e-5, 1e-5 on the practice opponent "strong".

The models (17 GB, not included)

  • Base. google/gemma-3-270m-it: 18 layers, width 640, 4 query heads and 1 key/value head per layer, vocabulary 262,144, tied embedding and output layer.
  • Three pairs (ids 100, 101, 102 = Pair 1, 2, 3). Each pair has an honest and a sycophantic fine-tune with the same seed, data order, and schedule.
  • What is trained. Each fact is asked three times: with the correct answer as the user's guess, with a wrong guess, and with no guess. The reply is always "The answer is {answer}." The honest model gives the correct answer every time. The sycophant gives the guess when there is one. Both models see the same prompts and the same set of replies. Only the pairing differs.
  • Settings. AdamW, learning rate 2e-5, 10 warm-up steps, cosine decay to 10%, batch 8, 3 epochs (336 to 342 steps), loss on the answer only. The token embedding is frozen, so it is the same in both models.
  • Behavior. On held-out known facts the sycophant follows 100% of wrong guesses in all three pairs. The honest model follows 2.8%, 0.7%, and 0.7% (the post rounds this to 1 to 3%). Both answer 98 to 99% of plain held-out questions correctly. The untouched base model already follows every wrong guess.
  • Dataset. 452 simple facts (capitals, sums, products, colors, opposites, legs, next day or month, continents, languages, number words). A fact stays if "The answer is {correct}." has a higher log-probability than 3 other answers of the same type. Each split has 146 to 147 held-out and 298 to 302 training facts.

The setup

  • Editor. Astra at effort max. One conversation for each run. The harness starts a fresh conversation every 40 turns (the handoff).
  • Model edited. The text part of the public Qwen/Qwen3.5-0.8B (24 layers), thinking on.
  • What Astra had. (1) A persistent Python kernel over the weights: CPU only, no GPU, no internet, at most 300 code runs. It loads a tensor, computes, and calls save_edit(name, tensor). (2) Practice problems with answers: 7,469 from GSM8K train, 7,275 from MATH train, and 714 AIME problems (answers only). (3) A forward-pass tool with a budget of 10, 25, or 50 passes. A pass is either a generation of up to 512 practice answers (a "both" pass gives a paired comparison of original and edited weights, 256 each), or a teacher-forced read of up to 1,024 texts (log-probabilities, hidden states, MLP activations, attention). A failed request does not count. A pass costs one pass at any size (notice 001).
  • Forbidden. Gradient descent or any training (no backward passes, autograd, optimizers, or iterative fitting). Running the model in the kernel. Internet. save_edit refuses edits to the final norm, to the embedding and output layer, and edits that only multiply a whole tensor by a constant.
  • End of a run. The run goes on until all passes are used. Then Astra makes a final choice and replies without code. It never saw the benchmarks.
  • Explanations. From an early turn (52 in p10c, 16 in p25c, 29 in p50c) the harness asks for a plain-English explanation before each code block. A block without one is sent back unrun.
  • Evaluation (hidden). The submitted tensors are cast to bfloat16 and replace the originals (code/build_ckpt.py). vLLM runs the chat template with thinking on. User message: problem + "Please reason step by step, and put your final answer within \boxed{}". Temperature 0.6, top_p 0.95, top_k 20, presence penalty 1.5, at most 32,768 new tokens. The last \boxed{} answer is graded with math-verify. Samples per problem: MATH-500 4, GSM8K 2, AMC23 16, Minerva 4, OlympiadBench 4, MMLU-Pro 1 (fixed 1,000 questions), GPQA Diamond 4, IFEval 2 (strict, on the answer after </think>).

How to rebuild an edited model

Each run's edit/ folder stores the submitted edit as an exact diff from the public base weights (revision 2fc06364…). Small edits are stored as changed entries (indices and new bfloat16 values). The p10c edits touch almost every entry of 30 matrices, so they are stored as rank-one factors plus a few rounding entries. code/apply_edit.py rebuilds the evaluated tensors bit for bit and checks every hash. In p50c, 130,188 of the 131,072 touched weights differ from the original after rounding to bfloat16.

Verify the 131,072. The post says 131,072 weights. The README gives 2 layers × 64 columns × 1,024 rows. The count is in runs/p50c/edit/manifest.json (64 changed columns per tensor).

The Gemma follow-up

Gemma 3 270M IT rarely loops (8.5% of MATH-500 answers reach the token limit, against 93% for Qwen). The follow-up asks if edits can raise math ability that no failure hides. Astra could not do this: no edit moved MATH-500 by more than about a point.

  • Method (prompt version 5). Fix a DEV set (to choose edits) and a HOLDOUT set (only to confirm them) before any edit. Screen edits with full-size passes. Freeze the best candidate before the HOLDOUT. At the end, submit the best edit found, even if the gain is not significant, and report it honestly.
  • Budgets. 5, 10, 25, and 50 passes. A generation pass answers up to 2,048 practice problems (1,024 per model in a paired pass).
  • Evaluation. MATH-500 only, 4 samples, temperature 1.0, top_k 64, top_p 0.95, 8,192 new tokens, no thinking. The grading is lenient: the last \boxed{} answer, else the answer after "Final Answer" or "the answer is", else the last number. The strict boxed-only scores are 2.8 (base) and 3.5, 3.1, 3.8, 2.6 (edited).

§9What is not in the repository, and known quirks

Not included

  • The Gemma fine-tunes of E7 (17 GB). The data, the training script, and the hashes are there, so a reader can rebuild them.
  • Intermediate files that the model wrote: activations, generated-text dumps, and draft networks. The final networks and weight edits are included. E8's edits are exact diffs against the public base weights, with a script that applies them.
  • The text of E3's Python corpus. It is other projects' code. A manifest and a rebuild script replace it.
  • GPQA question texts in E8's generations. GPQA's scores and per-question results are kept.
  • The agent harness code for E8 (prompts, sandbox, forward-pass server), and the IFEval and multiple-choice graders that evaluate.py imports. The rules that the harness enforced are in the prompts.
  • PPO checkpoints for E5. Only the results are given.
  • Trial runs of earlier prompt versions.

Quirks that a reader can meet

  • E3 true_copy_heads uses cut-off 0.3. The post uses 0.2.
  • E8 GPQA base score: interim 24.5 in the post figure, final 22.7 in the files.
  • E5 first reading of two replies had errors. The reader was fixed. The same replies were read again.
  • E4 ppo_training_result.json has "best_*" fields from the training run's own selection rule. That rule picked the untrained start (chunk 0). The network that Astra got is the final one (chunk 20).
  • E1 and E2 have one "error" item in each event stream. It is only a Codex notice that code mode is off.
  • E7 tool calls start at number 5, because of the crash on the authors' side.
  • Hard-coded paths in kept scripts point to the authors' machines.
  • Token counts in run.json add up inside one conversation. Do not sum them over turns.
