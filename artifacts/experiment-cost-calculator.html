5Where the numbers come from

  • Exact rows. The sum of audit.usage in every run.json, taking the largest value in each conversation, because the post's README says tokens accumulate inside one conversation. Cached input is a subset of input. Reasoning tokens are a subset of output.
  • Check. My own count with o200k_base gave 70,254 tokens for the Experiment 1 prompt. Codex reported 73,749. For Experiment 2: 96,296 vs 99,791. For Experiment 4: 351,708 vs 355,201. The gap is about 3.5k tokens of fixed overhead.
  • Seed rows. Built from those exact runs: Seed C uses the p50c run, Seed E uses one attention-tool conversation (about 19 turns), Seeds A and B use an Experiment 5 reply (about 6k in, 25k out), Seed D uses the Experiment 1 prompt size (73.7k in, 1.7k out).
  • GPU rows. My estimates, not measurements. The Qwen evaluation estimate follows from the 93% truncation rate at a 32,768-token cap, which makes each MATH-500 evaluation about 60M generated tokens. The PPO rate is an assumption.
  • Not modelled. Failed retries, tool servers, storage, and any price tier, long-context surcharge or batch discount your account may have.
